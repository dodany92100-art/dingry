Analyse DINGRY : catalogue, images et écart CRM / vitrine
Je n'ai pas l'erreur exacte, donc la Q1 reste conditionnelle. L'écart CRM / site (le vrai problème) est lui entièrement explicable par le code fourni.
5. Explication à l'utilisateur (5 lignes)
	1	Le site affiche une liste de produits écrite dans le code (PRODUCTS), puis y superpose ce qui est dans le CRM.
	2	Quand vous supprimez une fiche dans le CRM, vous retirez la superposition, pas le produit du code.
	3	Il ne disparaît du site que s'il a été marqué « retiré » (tombstone), ce que le code ne fait que pour les produits du seed.
	4	Passer un produit en brouillon ne le cache pas non plus : le brouillon est ignoré, donc la version du code réapparaît.
	5	Le CRM est donc un calque sur le site, pas la source du site. Le correctif consiste à faire que ce qui est géré en admin = ce que voient les clients.
Cause technique
overlayShopCatalog part de fallback.map(...) (donc de PRODUCTS) et n'enlève que les ids présents dans removed. Trois trous en découlent :
	•	Ids hors seed. removeProduct ne crée un tombstone que si SEEDED_PRODUCTS.some(...). PRODUCTS contient des ids absents de SEEDED_PRODUCTS (1, 3, 5, 8, 12 à 16, 20…). Supprimés dans le CRM, ils restent sur le site.
	•	Brouillons. toCatalogProduct renvoie null pour un draft. Le produit n'est plus dans live, donc le fallback statique reprend la main.
	•	Suppressions directes en base. Elles ne passent pas par removeProduct et ne créent donc aucun tombstone.
Deux aggravants :
	•	Côté client, use-shop-catalog.ts initialise l'état à PRODUCTS. Les produits supprimés s'affichent donc un instant avant le fetch. Sur une réponse non-OK ou une exception, il repasse à PRODUCTS (l'état "error" n'est jamais utilisé).
	•	Côté serveur, overlaySupabaseProducts renvoie le snapshot seed si Supabase a 0 produit. Vider la table ne vide donc pas le site. Et removed.length > 0 ? removed : store.removedCatalogIds empêche de « vider » les tombstones.

Lecture Supabase
Les URLs Cloudinary en dur ne font jamais échouer un build, sauf si next.config n'autorise pas le domaine dans remotePatterns. Lancez npm run check:prod-env avec les variables de prod.
Incohérence repérée : check-prod-env annonce R2_PUBLIC_BASE_URL comme requis, mais isR2ImageStorageEnabled() ne l'exige pas. Sans cette variable, les uploads partent bien dans le bucket, mais l'URL publique pointe vers R2_DEFAULT_PUBLIC_BASE (valeur en dur). Si ce n'est pas le bon domaine, les images s'uploadent et ne s'affichent pas.
Q2. Quelle procédure de nettoyage ?
Nettoyage ciblé, pas de reset Supabase ni de purge R2.
	•	Supprimer les images du CRM n'abîme pas la vitrine. Les produits seed pointent vers Cloudinary, et deleteBlobOrLocal n'y touche pas (ni R2, ni Blob, ni local). Seules les images uploadées via l'admin sont supprimées.
	•	Un reset Supabase est risqué. Avec 0 produit, le store retombe sur le seed et le site garde tout. Vous perdriez en plus vos fiches et vos tombstones.
	•	Une purge R2 casse les produits live qui pointent vers R2.
	•	Les orphelins R2 (images de produits supprimés) se nettoient par différence : clés du bucket moins URLs référencées en base. Pour être sûr de ne rien casser, comptez imageUrl, imageBackUrl et les images de options. Faites un dry-run, puis supprimez.

	•	Les trous de tombstone et de draft (diffs A et B).
	•	Le fallback client (PRODUCTS en initial et en erreur) : voir C.
	•	tombstoneCatalogPair supprime les lignes verso via deleteSupabaseProduct(extra) sans supprimer leurs images, ce qui laisse des orphelins R2.

Diffs minimaux
A. Les brouillons masquent le fallback (lib/shop-catalog-snapshot.ts). Cette fonction alimente à la fois le cache API et le checkout.
export function removedCatalogIdSet(store: AdminStore): ReadonlySet<number> {
  const ids = new Set<number>();
  const add = (raw: string | number) => {
    const id = Number(raw);
    if (Number.isInteger(id) && id > 0) ids.add(id);
  };
  (store.removedCatalogIds ?? []).forEach(add);
  for (const product of store.products) {
    if (product.publishStatus === "draft") add(product.id);
  }
  return ids;
}

Q9. Que faire de PRODUCTS en prod ?
Le retirer de la vitrine publique (flag Q7) mais le garder dans le dépôt comme source d'import, pour les tests et éventuellement pour un mode dégradé explicitement signalé. Ne pas le supprimer d'un coup : checkout, personnalisation et paires recto/verso en dépendent.
